总则与适用范围
1.1 目的
本规格书旨在定义“如语言”输入法 v7.1 版本的底层拆解规则、数据结构及端侧AI补偿机制。本文档作为前端渲染、后端引擎开发及AI模型训练的唯一权威技术依据。

1.2 适用对象
客户端开发工程师、算法工程师、QA测试工程师及交互设计师。

1.3 核心工程原则
文化本体优先：笔画数核定与部件拆分严格以传统书法笔顺及《说文解字》造字逻辑为准，而非现代检字法。
零特例铁律：29个基元键位对应关系绝对固定，运行时禁止任何硬编码的例外判断（No Hardcoded Exceptions）。
优雅降级：当直接拼合失败时，必须无缝切换至AI笔画补偿链路，确保用户输入体验无感知中断。

基元映射表（29-Key Matrix）
以下为键盘物理键位到逻辑基元的唯一映射，禁止运行时动态修改。
键位ID   基元类型   显示符号   内部编码   书法笔顺/工程备注
K01-K04   基础笔画   横 竖 撇 点   S_H, S_S, S_P, S_D   捺归入点(S_D)；折笔由组合推导

K05-K09   五行基元   金 木 水 火 土   W_J, W_M, W_S, W_F, W_T   独立语义场，不参与笔画拆解

K10-K29   核心偏旁   口 扌 日 月... 阝   R_KOU, R_SHOU... R_FU   R_FU(阝) = 3笔正写，左右耳同源

K30   功能键   ️   FUNC   候选词切换/设置/符号面板

️ 关键约束：R_FU (阝) 的内部权重与其余19个偏旁完全等同。拆解引擎中严禁存在 if (component == '阝') 的特殊分支。左耳旁与右耳旁的语义区分，必须通过上下文语境向量自动推导。

拆解引擎技术规范
3.1 输入处理流水线
[用户按键序列] → [前缀树匹配] → {命中?}
├─ YES → [输出整字/词组]
└─ NO → [AI字形补偿模块] → [置信度过滤] → [输出候选]

3.2 直接拼合规则
最大码长：4键（含功能键）。
匹配策略：贪心最长前缀匹配 + 位置标记消歧。
位置敏感性处理：如“阝”在内部编码中统一为 R_FU，通过前后文语境向量自动区分语义（如“陈” vs “都”），无需用户手动选择左右。

3.3 AI字形补偿协议
针对复杂部件（如“竹”系）的降级处理机制：
参数   规格   说明
触发条件   前缀树未命中且当前输入≥2笔   避免单笔画误触发

模型架构   Transformer-Lite (≤8MB)   端侧实时推理，延迟<15ms

种子数据集   38字(竹系) + 历史纠错日志   每周增量更新

置信度阈值   ≥0.92 直接上屏；0.75-0.92 置入候选区；<0.75 丢弃   防止噪声干扰

首候选命中率目标   ≥98%   低于此值触发模型热更新

数据结构与存储
4.1 静态词典格式
采用 DAWG (Directed Acyclic Word Graph) 压缩存储，内存占用 ≤ 1.2MB。

{
  "version": "7.1-Final",
  "checksum": "sha256:a3f8c2...",
  "entries": [
    {"code": "R_FU+S_S", "char": "阝", "type": "component"},
    {"code": "R_FU+W_M", "char": "陈", "freq": 9821, "pos": "left"},
    {"code": "S_P+S_H+S_D", "char": "竹", "type": "ai_compensate", "seed": true}
  ]
}

4.2 运行时状态机
空闲态 (Idle)：等待首键输入。
拼合态 (Parsing)：已输入1-3键，前缀树活跃节点 > 0。
补偿态 (Compensating)：前缀树失活，AI模型接管，UI显示“”微动效提示用户。
确认态 (Confirmed)：候选词选中，重置状态机并记录反馈日志。
